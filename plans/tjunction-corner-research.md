# Research: How established tiling/procgen systems resolve an under-representable T-connection

**Question:** When a cell needs 3 connections (a "T") but the available piece geometry can only represent 2 non-opposite connections (a "corner"), how do established autotiling / WFC / rule-tile systems decide which 2 of the 3 to keep?

**Context:** Mystery of the Scarab is retiring `WallTjunctionPrefab` (branch connector measured ~0.32 units off true cell-boundary midpoint) in favor of always resolving 3-tag wall cells to a Corner piece (~0.07 off, accurate). Question: for a 3-tag cell (one "mandatory" direction with no opposite present, one "opposite pair"), which of the two opposite-pair directions should the Corner join with the mandatory direction? An existing ad-hoc room-topology-walk heuristic (`WallSliceHelpers.TryComputeHypothesisCornerRotation`/`WalkToRoom`) scored 4/7 against manual human placement.

---

## 1. Autotiling / marching-squares conventions

**Marching squares ambiguity (the closest numerical analog).** The original marching squares/cubes technique (Lorensen & Cline, SIGGRAPH 1987, for the 3D case; the 2D case is an unpublished simplification commonly derived from it) has exactly two ambiguous cases out of 16 — cases 5 and 10, the "saddle" configurations where diagonally-opposite corners share a sign. These are the closest formal analog to a 3-tag "which way does it lean" problem, though topologically they're a diagonal ambiguity, not a T-vs-corner substitution.

The standard resolution is the **Asymptotic Decider** (Nielson & Hamann, "The Asymptotic Decider: Resolving Ambiguities in Marching Cubes", IEEE Visualization 1991) — summarized by Boris ("BorisTheBrave", *Resolving Ambiguities in Marching Squares*, boristhebrave.com, Jan 3 2022, updated Feb 28 2025): compute `Q = top_left × bottom_right − bottom_left × top_right` from the cell's four corner *scalar values*, and the sign of `Q` picks the topology. **Critically, this tiebreak is only possible because marching squares has continuous scalar data at each corner to interpolate** — it is not a bitmask-only convention. A discrete N/E/S/W tag system (like this wall generator) has no equivalent scalar field to sample, so this specific mathematical tiebreak does not transfer. No T-case-specific convention is documented anywhere in this source; the disambiguation is purely about the diagonal saddle case, not a "3 tags, 2-piece geometry" substitution.

**Autotile/bitmask tilesets (Godot, Tiled, RPG Maker) — all assume tileset completeness, not substitution.**
- **Godot 4 TileSet terrains**: each tile declares 3×3 "peering bits" describing which of its edges/corners connect to the terrain; the engine "looks at the surrounding cells and picks the tile whose peering bits best match the actual neighbors" (per Godot terrain-system explainer material; official reference: [Godot docs, Using TileMaps → Terrains](https://docs.godotengine.org/en/stable/tutorials/2d/using_tilemaps.html)). Multiple independent write-ups (e.g. UhiyamaLab, "Setting Up Autotiling with the Terrains Feature", 2025-06-20) treat missing coverage purely as an authoring bug: "Missed Peering Bits show up as 'one weird tile right there' or 'a gap in the border.'" No fallback/best-match-when-nothing-matches behavior is documented; the burden is on the tile author to cover every case.
- **Tiled terrains/Wang tiles** (official docs, [doc.mapeditor.org/en/stable/manual/terrain](https://doc.mapeditor.org/en/stable/manual/terrain/)): "it is not necessary for a terrain set to have all possible patterns, especially when using more than 2 terrains" — but the only documented behavior for a genuinely missing combination is **terrain-chaining through an intermediate terrain** (e.g., no direct dirt→cobblestone transition tile exists, so "the Terrain tool first inserts transitions to sand and from there to cobblestone"). This is a completeness workaround for terrain *type* combinations, not a geometric under-representation problem, and it has no analog for a single wall cell that needs a literal 3rd direction.
- **47-tile "blob" autotile sets** (the RPG Maker-style convention, also used by Godot/Tiled/Unity Tilemap content): the 256 raw 8-neighbor bitmask combinations collapse to 47 unique visual cases because "a corner only matters if both of its adjacent sides are also filled" (per multiple independent tileset-vendor technical write-ups, e.g. Rasterloom's "Why an auto-tiling terrain set has exactly 47 tiles" and CSAF's Verdant devlog, itch.io, 2026). CSAF explicitly frames an incomplete 47-set as **broken**, not resolvable: *"A 47-mask set missing three tiles is broken in your map — so this pack enumerates its transitions instead of drawing them."* The universal answer in this whole family of systems is: **cover every case at authoring time; an incomplete tileset is a content bug, not something the runtime algorithm is expected to paper over.**

**Conclusion for §1:** No primary source documents a standard convention for substituting a 2-way piece for a required 3-way (T) connection. Every established autotiling system's answer to incompleteness is "the artist didn't finish the tileset" — the fix lives in content, not in a resolution algorithm.

## 2. Wave Function Collapse / constraint-based solvers

Primary source: [mxgmn/WaveFunctionCollapse](https://github.com/mxgmn/WaveFunctionCollapse) README (Maxim Gumin).

- **Cell selection** uses a minimal-entropy heuristic: *"Find a wave element with the minimal nonzero entropy... Collapse this element into a definite state according to its coefficients and the distribution of NxN patterns in the input."* This is a genuine entropy-based tiebreak, but it operates over *which cell to resolve next*, and resolves that cell according to the *frequency of patterns in the training data* — it presupposes the tileset/pattern-set can legally satisfy the neighborhood, not that a lesser piece must be substituted.
- **Contradiction handling**: *"It may happen that during propagation all the coefficients for a certain pixel become zero. That means that the algorithm has run into a contradiction and can not continue."* The README further notes the general satisfiability problem is NP-hard, so WFC has no guaranteed-correct fast solution — contradictions are simply a failure state (in the base algorithm), not resolved by falling back to a weaker piece. Backtracking is described as a *known extension* other authors built on top (cited in the README: Karth & Adam M. Smith's paper on backtracking heuristics in WFC), not part of the original algorithm.
- **Directly on-point finding** — Boris the Brave, *"Wave Function Collapse Tips and Tricks"* (boristhebrave.com, Feb 8 2020), a WFC practitioner and cited contributor to the WFC ecosystem, states the actual behavior for an incomplete tileset: **"If you miss out a few tiles, WFC doesn't care. It'll plan around that and never build configurations that require those tiles."** For road/path networks specifically he recommends *excluding T-junction tiles entirely, or giving them very low weight*, so WFC simply avoids generating a 3-way junction rather than ever being forced to approximate one with a 2-way piece.

**Conclusion for §2:** WFC's answer to "the tileset can't represent this configuration" is categorically different from this project's constraint: **WFC avoids ever generating the configuration in the first place** (by excluding/weighting-down the connectivity pattern during generation), rather than generating the configuration and then improvising a substitute piece at placement time. That option isn't available here — Mystery's layout generator already commits to room adjacency/doors upstream of wall-piece selection, so by the time a 3-tag cell exists, avoidance is no longer on the table. This confirms the problem as posed (pick a substitute after the fact) sits **outside what WFC is designed to solve**; it is not "WFC's problem" as the task brief suspected — it's a downstream authoring/heuristic decision that only exists because upstream generation allowed a topology WFC would have simply forbidden.

## 3. Unity RuleTile (com.unity.2d.tilemap.extras)

Primary sources: [RuleTile.md](https://github.com/Unity-Technologies/2d-extras/blob/master/Documentation~/RuleTile.md) and `RuleTile.cs`, Unity-Technologies/2d-extras.

- Matching is authored per-rule as a 3×3 neighbor grid (Don't Care / This / Not This); *"If all of the neighbors of the Rule Tile match the options set for their respective directions... the Rule is considered matched."*
- **Ambiguity between multiple matching rules is resolved by authored list order, not by any geometric or contextual heuristic**: *"When matching Rules during the placement of the Tile, the Rule Tile algorithm will check the first Rule first, before proceeding with the next Rules."* The doc's own guidance for authors is to order rules by frequency/specificity (put common/more-specific cases first) — i.e., **the tiebreak is a human-authored priority list**, evaluated deterministically, first-match-wins.
- Rotation/mirror matching (`Rotated`, `Mirror X/Y/XY`) auto-generates additional match attempts by transforming the 3×3 neighborhood and retrying, but this is about *finding* a match, not about *choosing* between two valid-but-incomplete geometric interpretations of the same neighborhood.
- Nothing in RuleTile addresses "the matched rule's output piece can't fully represent the matched neighborhood" — RuleTile has no notion of a piece being geometrically insufficient for its matched connections; that failure mode simply isn't modeled.

**Conclusion for §3:** RuleTile's only mechanism for resolving ambiguity is **deterministic, author-ordered priority — a simple fixed rule, not a runtime-computed heuristic.** This is the most directly relevant primary-source precedent for the exact kind of tiebreak being designed here, and it favors option (b)-style simplicity over topology-aware inference.

## 4. Other established write-ups on the T-piece-missing-from-tileset scenario

Search across dungeon-generation blogs (Boris the Brave's *Dungeon Generation in Diablo 1 / Unexplored / Binding of Isaac / Enter the Gungeon* series), tileset-vendor devlogs, and GDC-talk-adjacent material did **not surface a named, dated, primary source that documents this exact scenario** (tileset physically lacks a T-piece, must substitute a 2-way corner, and states a principled tiebreak for which 2 of 3 directions to keep). This should be flagged clearly: **no confirmed primary source addresses this precise question.** The closest adjacent material:
- Blob-tileset vendors (§1) treat a missing T-case as a content defect to be fixed by drawing the tile, not resolved algorithmically.
- Boris the Brave's WFC guidance (§2) treats it as a case to be *excluded from generation*, not substituted after the fact.
- Tiled's terrain-chaining (§1) substitutes via an *intermediate terrain type*, which has no structural analog to "there is no third piece type available at all."

No source claims there is a universally "correct" direction to prefer (clockwise-first, toward-open-space, etc.) for this kind of substitution. This appears to be treated everywhere as an authoring decision, not an algorithmic one.

---

## Recommendation

**None of the primary sources examined validate a universal, principled runtime rule for this exact situation** — every established system either (1) requires the tileset to be complete and treats gaps as content bugs to fix by drawing the missing piece, or (2) actively avoids ever generating the under-representable configuration in the first place (WFC), which isn't available to Mystery's pipeline since layout/doors are already committed before wall-piece selection runs. There is no cited authority for "walk the room topology to find open space" as a standard resolution technique — it does not appear in any of the primary sources surveyed, and empirically it underperforms (4/7, only marginally better than chance) against manual human placement.

The one directly relevant, well-documented precedent — **Unity RuleTile's own ambiguity resolution** — favors the simplest option: a **fixed, deterministic, author-ordered rule**, evaluated the same way every time, with no contextual/topological inference. That supports **(b): a simple fixed deterministic rule** (e.g. always resolve to whichever opposite-pair direction comes first in a fixed clockwise order from the mandatory direction) as the most consistent choice with how these established systems actually resolve match ambiguity — deterministic and cheap over clever.

Given that (i) no source claims a fixed rule will be geometrically/aesthetically correct 100% of the time, and (ii) every source that discusses incomplete tilesets ultimately routes the real fix back to authoring/content correction, the strongest overall recommendation is a **hybrid of (b) and (c)**: ship the simple fixed deterministic rule as the automatic default (cheap, predictable, easy to reason about and debug), and treat any cell it gets wrong as expected, correctable content — exactly the same posture Tiled, Godot and the blob-tileset vendors take toward "the tool did its best, a human finishes the edge cases." Do not invest further in the room-topology-walk heuristic (option a): it has no supporting precedent in the systems surveyed, it's already measured as weak (4/7), and it adds inference complexity that these established systems specifically avoid in favor of deterministic, authored rules.
