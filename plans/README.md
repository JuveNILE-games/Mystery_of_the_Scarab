**Fresh-eyes follow-up session (2026-09-22, seed `1919335568`) — re-investigated

- **Items 1 + 2 — FIXED together, uncommitted.** Turned out to be the same
  underlying design gap, not separable as originally scoped: item 1's fix
  alone (making the door branch call `DetermineOutwardDir`, matching every
  other placed piece) was necessary but insufficient, since every door cell
  is, by construction, a genuine 2-room opposite-pair divider (a door
  connects exactly two rooms across their shared boundary), and
  `DetermineOutwardDir` deliberately keeps dividers centered — so the call
  now happens but always returns null for a normal inter-room door.

  Item 2's real fix, `RoomShellAssembler.ReconcileRunOutwardDirs` (a new
  post-process pass between the main placement loop and
  `ShellAlignmentPass.Align`), resolves this: walks each maximal
  same-orientation, run-axis-adjacent chain of Straight-shaped wall/door
  instances in cell order, and fills a null-verdict cell only when
  sandwiched between (or trailing) an anchor whose verdict is known — for
  an interior gap between two anchors, only when they agree. A naive
  "whole connected run votes" policy was tried first and found too coarse
  (one unrelated disagreement anywhere in a long run vetoed every local fix
  on it); the shipped version fills locally instead. Handles the
  multi-cell-door caveat correctly — a door only registers one grid cell as
  its `cellByInstance` anchor, so run-adjacency walks through its *full*
  `DoorCells` span (threaded in via `doorCellsByInstance`), not just that
  one cell, so a genuinely two-sided door is correctly seen as two-sided
  rather than picking an arbitrary side.

  Test-first: `Assets/Game/Tests/RoomShellAssemblerRunReconciliationTests.cs`
  (supersedes the deleted `RoomShellAssemblerDoorAlignmentTests.cs`, whose
  premise — every door must match every same-rotation wall neighbor — was
  itself wrong, since a genuinely opposed door correctly stays mismatched).
  Verified red before the fix, green after. Full EditMode regression:
  281/282 both before and after (the 1 failure is the same pre-existing,
  unrelated one noted above — confirmed unchanged by this fix). Live
  re-verified against a brand-new seed (`424242`, never baked before this

- **Item 5 — FIXED, uncommitted (2026-09-23): door mesh clipping into
  independently-placed neighbor walls.** Found live-inspecting a selection
  on seed `555555`: `Door.prefab`'s mesh is always a fixed 3-cell-wide
  module, but when `BspLayoutGenerator.WidenDoorway` correctly refuses to
  widen a doorway's `DoorCells` (the neighboring topology doesn't support a
  clean border to grow into on one or both perpendicular sides — confirmed
  this refusal is itself correct, by-design behavior, not a bug), the
  connection falls back to a single `DoorCells` entry, but the door's real
  mesh still physically spans 3 cells. `RoomShellAssembler`'s per-cell
  placement loop only excludes cells actually listed in `DoorCells`, so the
  door's immediate neighbor cell(s) each got their own independently-placed
  `WallStraightPrefab`, which then physically overlapped the door's
  oversized mesh at a different Z depth (shifted vs. centered), reading as
  visible clipping. Confirmed live: Door at `(13,9)` (seed `555555`, mesh
  X=[11.5,14.5]) overlapped independent walls at both `(12,9)` and
  `(14,9)`; the same pattern also existed at door `(13,4)` on the original
  seed `1919335568`, previously undetected.

  Fixed by `RoomShellAssembler.RemoveWallPiecesOverlappingDoors`, a
  post-alignment cleanup pass: for every door, measure its real combined
  world bounds and remove any other placed instance whose bounds
  genuinely overlap it (volumetric overlap on both axes, not merely
  touching). Runs against final, real geometry rather than trying to
  predict the door's footprint from topology. Test-first
  (`RoomShellAssemblerDoorOverlapTests.cs`), confirmed red before, green
  after.

  **Diagnosis note**: the fix's first version used
  `Undo.DestroyObjectImmediate` (matching this file's existing
  create-with-Undo convention) and caused 5 severe, full-suite-only
  failures elsewhere (`NullReferenceException`s in
  `LevelBakerRoomShellReconcilerSteadyStateTests`, a null level root in
  `LevelBakerSpareConnectionTests`) — each test passed fine in isolation,
  only failing as part of the full 283+-test run. Isolated by disabling the
  new pass entirely (confirmed the 5 failures disappeared) and by testing
  plain `UnityEngine.Object.DestroyImmediate` instead — the plain form
  fixed all 5. `Undo.DestroyObjectImmediate` is for interactive
  Ctrl+Z-supporting Editor workflows; using it for editor-tool/batch
  cleanup that runs across hundreds of sequential EditMode tests in one
  session appears to corrupt Undo-system state in a way that only
  surfaces several tests later, not in the test that triggered it. Use
  plain `DestroyImmediate` for this kind of automated bulk deletion, not
  `Undo.DestroyObjectImmediate`.

  Fixing this also revealed that `door(13,4)`/`(13,9)`'s immediate

  their neighbors *before* this cleanup pass removes them).

- **Item 6 — FIXED, uncommitted (2026-09-23): `TryCarveNotch` breaking
  normal 1-cell shared walls into inconsistent double-thickness dividers.**
  Found live-inspecting the same seed-`555555` selection as Item 5:
  `Room_002`/`Room_004` shared a normal 1-cell wall at row `z=16` (matching
  every other room-adjacency pair in the level — 25 of them, all
  consistently 1-cell), but a 2-cell gap at rows `z=10`-`15`. Root cause:
  `BspLayoutGenerator.TryCarveNotch` (the `IrregularRoomCount` shape-variety
  feature) removes a rectangular block from one corner of a room's footprint
  with no awareness of neighboring rooms — here it removed `Room_002`'s
  cells at `(7,10)`-`(7,15)`, pushing that stretch of its boundary back by
  one cell and widening what used to be a clean 1-cell shared wall into 2
  cells. `RoomShellAssembler` then placed two independent walls that shift
  flush toward each other and meet with zero gap, reading as one solid
  double-thickness dividing wall. This is the previously-flagged, deferred
  root cause from this file's Origin section ("`BspLayoutGenerator.
  TryCarveNotch` leaving single-cell peninsulas... worth a follow-up plan
  once someone characterizes exactly what shape those cells need") — this
  is that follow-up, and the double-thick-wall symptom was a previously
  undescribed consequence of the same root cause.

  Fixed in `TryCarveNotch`: before committing to a candidate notch corner,
  check whether any cell it would remove was the room's own boundary
  directly across a clean 1-cell wall gap from another room (i.e. would
  widen a normal shared wall into 2 cells). If so, try the other 3 corners
  in a fixed, deterministic order (no RNG re-roll, so layouts stay
  seed-reproducible); if all 4 would break a clean adjacency, leave the
  room un-notched rather than guess. Test-first
  (`BspLayoutGeneratorNotchAdjacencyTests.cs`: no room pair may have both a
  1-cell shared wall and a 2-cell gap anywhere in the same bake), confirmed
  red before, green after.
