# Room Shell hand-edits survive re-bakes via a cell-anchored edit history, reconciled at Bake time

`LevelBaker`'s re-bake destroys and regenerates every object carrying a `PrefabBrushObject` marker for the Room Shell placement group, unconditionally (`LevelBaker.cs` ~505-510). This was correct for its original scope — excluding unmarked Gameplay Layer content from re-bake (SCARAB-007) — but it means any hand-edit made directly to an already-baked Room Shell object (a nudged wall, a fixed corner rotation, a clipping prop moved) is silently destroyed on the next re-bake, with no diff, warning, or merge. The existing workaround, pushing generic fixes into the shared wall-kit rule assets instead of editing baked instances, has no answer for a genuinely one-off, level-specific tweak, and actively discourages using hand-editing as a deliberate creative tool ("soul" additions a curator places by hand and expects to survive iteration on the generator).

We considered anchoring identity to `RoomId`, since that's the existing per-room identifier layout data already carries. Rejected: `RoomId` is assigned as a sequential generation-order index (`Room_{i:000}`, `Corridor_{counter:000}`) with no content-stable meaning — a generator *parameter* change (RoomCount, CorridorCount, anything that reshuffles split order) can renumber rooms wholesale even at the same seed, silently misattributing recorded edits to the wrong room. `RoomShellAssembler.BuildShells` already resolves an absolute grid cell per placed piece internally (`Dictionary<GameObject, Vector2Int> cellByInstance`, not currently persisted) — that's the only identity that's actually stable, independent of generation order. We also considered a live, chronological operation log (true Photoshop-style undo: move, then move again, then rotate, individually replayable/revertable) rather than a snapshot of latest state. Rejected as disproportionate: nothing in the motivating cases needs stepping back through *multiple* past edits to one object, only "the fix survives." A per-slot "latest known state" is sufficient and far simpler to build and reason about. We also considered requiring an explicit "lock this object" gesture before an edit is protected. Rejected in favor of automatic detection, matching this codebase's existing preference for safe-by-default behavior (Core's ADR 0005, "silence was the bug") — an explicit flag's failure mode is silently forgetting to set it, which is worse than automatic detection's failure mode (occasionally protecting an incidental, non-deliberate change).

**Decision**: `Bake()` gains a reconciliation pass, run before it wipes and regenerates:

1. **Capture.** Diff the current scene's Room-Shell-marked objects against the last-recorded generation snapshot (written by the *previous* Bake), keyed by grid cell + role, not `RoomId`:
   - Recorded in the snapshot, missing now → **delete**.
   - Present now, not in the snapshot → **add** (this covers both a genuinely new prefab and a duplicated existing wall-kit piece — a copy inherits the same `PrefabBrushObject` fields as its source, so marker type alone can't distinguish "generator output" from "hand-added copy"; only presence-in-the-last-snapshot can). Anchored to its nearest grid cell plus a local offset, since an added piece was never resolved to a slot by the rule system.
   - Present now, changed since the snapshot → **tweak** (new transform/state recorded).
   - Present now, unchanged → ignored; letting regeneration replace it with an identical fresh copy is harmless.
   All three outcomes are written into a persistent, level-scoped edit-history asset (parallel to `LevelConnectionCuration`'s per-level pattern).
2. **Generate.** Unchanged: wipe every Room-Shell-marked object, regenerate fresh from seed/rules/parameters.
3. **Replay.** Apply the edit-history on top of the fresh output, matched by cell + role: a delete entry suppresses the corresponding fresh piece; a tweak entry overwrites the corresponding fresh piece's state; an add entry re-instantiates its stored prefab at its anchored cell + offset. An entry whose target cell/role no longer exists in the fresh output (a room shrank, a rule change eliminated that piece) is dropped and logged — never silently discarded, never kept dormant.
4. **Snapshot.** Record the resulting scene (post-replay) as the new baseline for the next Bake's reconciliation.

Scope: tweak, delete, and add are covered (not, say, editing a Gameplay Layer object's own fields — that's already protected by simply not carrying the Room Shell marker). This only protects same-seed re-bakes; re-rolling the seed already re-rolls the shell entirely per the map's settled constraints, and no Room Shell protection is expected to apply there. A same-seed re-bake that also changes topology-affecting *parameters* (not just a rule-asset swap or a non-topological bug fix) will likely orphan most recorded edits, since the cells doing the same job can shift — this is treated as correct, reported behavior, not a bug to solve here.

**Consequences**: hand-editing a baked Room Shell and iterating on the generator (rule fixes, non-topological bug fixes) stop being mutually destructive — the checkpoint is each Bake, not each individual edit, so no extra workflow step is needed between edits. Deliberate hand-added "soul" content becomes a supported, survivable authoring technique rather than something re-baking silently punishes. The known, accepted limitation is that only the *latest* state per slot is kept (no multi-step history to revert through), and only edits anchored to a slot that still exists in cell-coordinate terms survive a parameter-driven topology change.
